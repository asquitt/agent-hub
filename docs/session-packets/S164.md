# Session Packet

## Segment
- ID: S164
- Deliverable(s): MCP Streamable HTTP discovery gateway
- Date: 2026-08-27
- Owner: Platform

## Objective
- Primary objective: turn the existing MCP declaration export into an authenticated protocol endpoint that real MCP clients can initialize, inspect, and call without duplicating discovery business logic.
- Success criteria: an official MCP SDK completes initialization and all discovery operations; OAuth tokens are bound to the exact MCP resource; tenant, scope, protocol, origin, and input boundaries fail closed; existing REST behavior remains compatible.

## Dependencies
- Required outputs: S07 canonical discovery and tool declarations, S34 live discovery index, and S163 identity/OAuth containment.
- Starting gaps: no `POST /mcp` transport, no protocol lifecycle, Protected Resource Metadata described the API root instead of the MCP resource, OAuth tokens had no resource audience, and exported MCP tools could not be invoked by a standard client.

## Scope
### In Scope
- Stateless MCP Streamable HTTP at `POST /mcp` with initialize, initialized notification, ping, tools/list, and tools/call.
- Real dispatch into canonical registry and discovery services for search, manifest retrieval, and compatibility checks.
- Scope-filtered tool visibility and execution enforcement.
- RFC 8707-style resource targeting, JWT audience verification, RFC 9728 Protected Resource Metadata, and `WWW-Authenticate` discovery challenge.
- Origin allowlisting, media-type negotiation, protocol-version handling, strict JSON-RPC and tool argument validation, tenant isolation, and non-echoing failures.
- Official MCP Python SDK interoperability proof against a real Uvicorn process.

### Out of Scope
- Authorization-code, PKCE, dynamic user consent, browser login, or public-client OAuth.
- Stateful MCP sessions, server-sent event resumption, subscriptions, prompts, resources, sampling, elicitation, and tasks.
- A2A transport execution, managed provider execution, remote deployment, or public endpoint proof.
- Capability/DID authority, API-key lifecycle, audit durability, OAuth client rotation/revocation, and policy-plane remediation tracked as later security slices.

## Implementation Plan
1. Add a closed-schema MCP dispatcher over canonical discovery services.
2. Mount a deny-by-default authenticated `/mcp` route with protocol-aware errors, origin validation, and media negotiation.
3. Bind OAuth client-credentials tokens to the exact MCP resource and prevent replay at generic REST endpoints.
4. Prove lifecycle, scope, tenant, malformed-input, and resource-replay behavior with direct HTTP regressions.
5. Prove interoperability with the official MCP SDK, then run static, boundary, packaging, deployment, browser, performance, and full-suite gates.
6. Record exact evidence, freeze the commit, and obtain independent exact-head review before publishing a stacked draft pull request.

## Verification Plan
- Protocol/API: official SDK plus direct JSON-RPC requests for lifecycle and all three tools.
- Security: invalid origin, unsupported version, malformed request, scope denial, tenant isolation, invalid resource, untargeted token, and cross-endpoint replay.
- Compatibility: existing auth/discovery/gate suites, route-policy snapshot, wheel packaging, and deployment containment.
- Release: changed-file Ruff/Pyright/compile, full pytest/JUnit, Playwright, immutable review, and exact branch/head/tree evidence.

## Acceptance Criteria
1. An official MCP client completes initialization, tool listing, and a canonical discovery call over real HTTP.
2. `/mcp` accepts only authenticated, policy-classified requests; exposed tools match granted scopes and calls re-check scope.
3. OAuth resource targeting produces an exact `aud`; invalid and untargeted resources fail at `/mcp`; targeted tokens cannot replay against generic REST APIs.
4. Cross-tenant manifest access fails without revealing the other tenant's record.
5. Malformed protocol and tool inputs return deterministic non-secret errors.
6. Proportional local gates pass on the final candidate and independent review admits no HIGH or MEDIUM finding.
7. Evidence does not claim authorization-code OAuth, stateful MCP, hosted CI, deployment, or autonomous provider execution.

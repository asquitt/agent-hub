# Session Packet

## Segment
- ID: S165
- Deliverable(s): Durable capability-token, DID, and verifiable-credential authority
- Date: 2026-08-27
- Owner: Identity

## Objective
- Primary objective: bind capability tokens, DIDs, and verifiable credentials to durable tenant-owned identities so authorization artifacts cannot be forged, replayed across resources, revived after lifecycle changes, or administered across ownership boundaries.
- Success criteria: issuance derives authority from typed authentication context; persisted artifacts survive restart; verification enforces audience, resource, revocation, and identity-generation snapshots; cross-boundary operations are nondisclosing; deactivation and revocation are monotonic.

## Dependencies
- Required outputs: S163 typed owner/tenant/agent authentication context, identity lifecycle generation, revocation-aware JWT verification, and SQLite identity migrations.
- Starting gaps: capability tokens are signed without ownership or lifecycle records; IP/resource caveats are skipped when context is omitted; DID and VC state is global process memory; routes discard authenticated actors; DIDs can be recreated after deactivation; arbitrary VC claims can replace the credential subject.

## Scope
### In Scope
- Additive identity migration for capability-token roots, DIDs, and verifiable credentials with immutable owner, tenant, issuer, subject, and generation snapshots.
- Typed-actor issuance, lookup, list, verification, attenuation, deactivation, and revocation through the canonical identity storage owner.
- Mandatory capability audience and resource binding, exact verification context, server-derived source IP, explicit token revocation, and legacy-token fail-closed behavior.
- Active same-boundary issuer/subject validation, agent-bound self authority, scope attenuation, monotonic DID deactivation, durable VC revocation, and reserved-claim rejection.
- Nondisclosing object authorization and deterministic malformed-input failures while preserving existing endpoint paths and response fields where secure.

### Out of Scope
- Accepting capability tokens as REST or MCP authentication credentials.
- Cross-tenant federation, public DID resolution, external DID methods, presentations, asymmetric signing, KMS integration, or full W3C conformance claims.
- PostgreSQL, multi-worker or multi-replica coordination, remote deployment, provider proof, or audit-log durability outside this artifact boundary.
- API-key lifecycle changes, OAuth client rotation, marketplace promotion, and autonomous provider execution.

## Assumptions
- The current SQLite identity store remains the single-process authority for this slice.
- Existing in-memory DID and VC data is development-only and is not migrated.
- Existing version-1 capability tokens intentionally fail closed after the version-2 persisted authority is introduced.
- The configured symmetric identity secret remains a local process secret; S165 adds domain separation and durable authorization state but does not claim KMS-backed signing.

## Implementation Plan
1. Add exploit-focused API and persistence regressions for ownership, replay, lifecycle invalidation, monotonic state, malformed input, and restart behavior.
2. Add an additive identity migration and canonical storage methods with owner-plus-tenant filtering and transactional mutation.
3. Refactor capability-token and DID/VC services to require typed actors, persist authority roots, and verify current identity generations.
4. Pass the authenticated request context and server-derived network context through the existing routes without duplicating access-policy logic.
5. Run focused, migration, policy, packaging, static, browser-proportional, and full regression gates.
6. Record exact evidence, freeze the candidate commit, obtain independent exact-head review, and publish one stacked draft pull request without automatic hosted CI.

## Verification Plan
- API/security: forged issuer, inactive identity, agent impersonation, cross-tenant object access, audience/resource replay, body-supplied IP spoofing, reserved VC claims, and malformed input.
- Lifecycle: explicit token/VC revocation, DID deactivation, identity suspension/revocation/reactivation, and generation mismatch.
- Persistence: close and reconfigure the identity store, then re-read and re-verify artifacts and terminal states.
- Compatibility: existing capability/DID tests, identity auth/revocation suites, route-policy snapshot, migration ordering, wheel packaging, and deployment containment.
- Release: changed-file Ruff/Pyright/compile, full pytest/JUnit, proportional Playwright, rendered DOCX inspection, immutable xhigh review, and exact branch/head/tree evidence.

## Acceptance Criteria
1. Every persisted authority artifact has immutable owner and tenant attribution, and every actor-facing query filters both.
2. Issuer and subject identities are active in the same authority boundary; agent-bound principals cannot act for another agent.
3. Capability tokens require persisted audience and resource bindings and reject missing or mismatched verification context.
4. Explicit revocation, DID deactivation, and issuer or subject suspension/revocation invalidate dependent artifacts immediately.
5. Reactivation or reconfiguration does not revive artifacts issued against an earlier identity generation.
6. A deactivated DID cannot be recreated, and VC/token revocation remains durable across storage reconfiguration.
7. VC issuer, subject, JWT-equivalent proof fields, and `credentialSubject.id` remain consistent; reserved claims cannot overwrite them.
8. Cross-owner and cross-tenant read, list, verify, revoke, and deactivate operations disclose nothing and mutate nothing.
9. Malformed payloads return stable 4xx responses without secret material or server errors.
10. Existing secure endpoint shapes remain compatible, legacy unbound capability tokens fail closed, and no capability-auth acceptance is introduced.
11. Proportional local gates pass on the final candidate and independent review admits no HIGH or MEDIUM finding.
12. Evidence does not claim hosted CI, deployment, federation, KMS, full standards conformance, or autonomous execution.
